# Сравнение C4-PlantUML и Structurizr DSL

## 1. Сколько раз «Backend API» встречается в .puml и сколько в .dsl?

В трёх .puml-файлах (01-context не считаем — там системы,
не контейнеры; берём 02-container, 03-component, 04-dynamic)
название «Backend API» встречается три раза. В workspace.dsl —
один раз: контейнер объявлен один, а виды ссылаются на него.

При переименовании в PlantUML нужно править три файла и не
забыть про связи. В Structurizr — одну строку, все виды
обновятся автоматически. Это и есть разница между
«диаграммой» и «моделью».

## 2. Что умеет C4-PlantUML, чего не умеет Structurizr DSL, и наоборот?

C4-PlantUML:
- точный контроль раскладки через hidden/together,
- вставка произвольных заметок note,
- смешивание C4 с обычными элементами PlantUML,
- работает без Docker и без интернета.

Structurizr DSL:
- одна модель — много видов, нет дублирования,
- автоматическая согласованность: удалили контейнер —
  он исчез из всех видов,
- поддержка нескольких тем оформления,
- экспорт в PlantUML, Mermaid, DOT и др.,
- версионирование модели как единого документа.

## 3. Какой уровень C4 оказался бесполезен для ИС библиотеки?

Уровень 4 (Code) — это диаграмма классов UML, она уже
сделана в ПР1. Дублировать её в C4 нет смысла: те же классы,
те же связи. C4 останавливается на уровне Component.

Из трёх верхних уровней наиболее полезен Container: по нему
новый разработчик за пять минут понимает, что где живёт.
Context полезен для заказчика, Component — для команды
Backend API.

## 4. Диаграмма компонентов UML и C4 Level 3 — в чём разница?

Диаграмма компонентов UML показывает компоненты как
развёртываемые единицы с интерфейсами и портами, часто
на уровне артефактов. C4 Level 3 — логические компоненты
внутри одного контейнера, без интерфейсов и портов.

Для учебной модели выбрал бы C4 Level 3: он не смешивает
логику и развёртывание, а для физического размещения есть
отдельная UML-диаграмма развёртывания.

## 5. Нужна ли диаграмма развёртывания UML?

Да. C4 Context/Container/Component не покрывают физическое
размещение: узлы, артефакты, порты. Для ИС библиотеки важно
показать, что api и worker живут в Kubernetes, БД — на
отдельном сервере, поиск — в отдельном кластере, брокер —
на третьем. Сделано в 05-deployment.puml.
